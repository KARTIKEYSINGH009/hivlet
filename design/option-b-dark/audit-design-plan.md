## Audit findings, in the brief's priority order
1. Dashboard dark mismatch, mostly fixed, not fully: no light cards were found in the searched app files, but `PageHeader` is 24px sans-bold, not 32px Georgia, section titles are sans semibold, not Georgia 22px, and dashboard shows six metrics, not four, with metrics before attention.
2. Approval decision clarity, weakest release-critical area: the card shows agent, action type, linked task, time, reason, and raw JSON payload, with gold Approve and a reject control. It does NOT show a plain-language WHAT WILL HAPPEN sentence, a consequence (destination, recipients, cost, reversibility), Connected by member, who decided (only a timestamp in history), a copy-payload control, an Approving state, or a payload-unavailable state. Reject uses bright red-300/red-700 on coal, which breaks the muted-red rule and is hard to read.
3. Status consistency, mostly in place, with label and extra-state gaps: `TaskStatusPill`, `AgentStatusPill`, `ApprovalStatusPill`, and `ExecutionStatusPill` already follow the neutral/working/waiting/success/failure mapping in most cases. Gaps: labels are lowercase because only the first underscore is replaced, so In progress and Awaiting approval render lowercase; agent detail and list do not consistently show Connected by member; tasks also carry priority and due date, which the brief says not to invent, so keep, hide, or remove that as a product decision, do not silently expand it.
4. Dashboard hierarchy: dashboard order is header, six metrics, recent reports, failed executions, recent activity, agents. Attention (pending approvals, work awaiting verification, failures) is not first, and pending approvals is only a metric number, not a linked attention row.
5. Task board readability: board is `lg:grid-cols-5` with no 280px minimum column width found in the grep, and no mobile single-list plus status filter was confirmed. Do not claim it is readable at 1440px or 360px until it is checked in a browser.
6. Member-agent ownership: agents are created with `member_id` and `created_by_member_id` in code, but the agents list grep did not confirm a Connected by member name in the rendered row. This is a data-display gap, not just a label gap, because member display names must come from a trusted source.
7. Keyboard focus, systematic gap: inputs use `focus:border-gold focus:outline-none`. That is exactly what the brief forbids as a substitute: no 2px gold outline, no 2px offset, and no focus treatment was found on links, buttons, tabs, menus, or task controls in the grep.
8. Auth completion: `components/auth-form.tsx` uses the same password placeholder for login and signup, "At least 6 characters", which is signup guidance on login. There is no forgot-password or recovery link in the form, no show/hide password, no paste or password-manager note, and loading says "Working…", not "Signing in…". Confirmation handling exists in code (session versus no-session notice), but resend is not in the form. Invitation continuity through `/join/[code]` was not inspected in this turn.
9. Empty and exceptional states: `EmptyState` exists and is used, but it is centred, dashed, and has no action, while the brief wants left-aligned, one sentence, one primary action. Loading, error, filtered-empty, and permission-denied are not consistently distinguished in the pages inspected.
10. Public preview credibility: homepage is gold and honest about early access and pricing, but it still has two nav bands (global header max-w-5xl, page max-w-6xl), a "Security" nav label pointing at Trust, "Explore the product" going to signup, a preview that is not labelled "Example workspace", and a Working pill in the hero that uses muted styling, not the gold working treatment. The brief also asks for sample numbers on preview metrics, which conflicts with the earlier decision to strip counts so they do not read as real results. That conflict needs a decision, not a silent change.

Other confirmed gaps: sidebar is ink, not coal, and 240px (`sm:w-60`), not about 224px; sidebar order is Overview, Tasks, Handoffs, Agents, Usage, Reports, Approvals, Activity, Get started, Settings, not the brief order; workspace main padding is px-4/py-8, sm:px-8, not 32px; activity and overview render raw event names with underscores replaced, not sentences; reports verification exists as one-tap verify, but the brief's per-deliverable versus report-level distinction needs a product check before relabelling.

## Shared component specifications, Review Desk
Use one source in `components/workspace-ui.tsx` plus `app/globals.css`. Do not patch pages one by one.

- Page: ink background, 32px desktop padding, 24px tablet, 16px mobile, content max about 1200px, task board may use full remaining width. Page header: Georgia title 32px/40px desktop, 28px/36px mobile, short context left, one relevant action right, no greeting banner, no giant rounded card around the app.
- Section title: Georgia about 22px/30px. Body: system sans 14px/22px. Item and task titles: system sans about 15px/22px, semibold where appropriate. Metadata: 13px/18px. Input text: 16px.
- Card: coal, hairline white 10%, 12px radius, 20px desktop / 16px mobile padding, no shadow, no gradient, no glow. Raised only for meaningful nested content.
- Primary button: gold background, ink text, gold-soft hover, 8px radius, 14px semibold, about 40px desktop / 44px mobile, 16px horizontal padding, stable width while loading.
- Secondary button: transparent or coal, ivory text, hairline border, raised hover, same geometry as primary.
- Text action: gold-soft, descriptive label, clear hover and focus.
- Input: raised inside coal forms, hairline border, 8px radius, 44px high, 12px horizontal padding, 16px text, visible label, helper or error below.
- Focus, everywhere: 2px gold outline, 2px outline offset, on links, buttons, inputs, tabs, menus, icon buttons, task controls, and navigation. A gold border alone is not enough. Keep focus visible inside scroll containers, do not clip it.
- Metric card: coal, 20px padding, muted label, ivory 28-32px tabular number, optional factual supporting line, no coloured icon square, no sparkline, no fake chart. Show real zero, never disguise loading or error as zero.
- Pill: about 24px high, 12px/16px text, 8px horizontal padding, full radius, always a text label, capitalised display label. Neutral (todo, idle, disabled, paused): raised, muted, hairline. Working (in_progress, working, running): gold background, ink text. Waiting (in_review, awaiting_approval, pending): coal/transparent, gold border, gold-soft text. Successful (done, succeeded, approved, verified): muted green text/border on dark. Unsuccessful (failed, rejected, error): muted red text/border on dark. Green is not online, red is not disabled, gold is for actions, working, and the waiting outline.
- Empty state: left-aligned, short heading, one explanatory sentence, one clear primary action, about 24px padding, no illustration. Examples: No agent, Connect your agent. No tasks, Create task. No pending approvals, View tasks. No filter results, Clear filters. Choose by role and setup state.
- Loading: static coal/raised placeholders, no gradient shimmer. Error: actual readable explanation plus a real retry or recovery action, never an empty list or zero metric.
- Approval card, single column, about 880-960px max: WHAT WILL HAPPEN first, then consequence, then WHO REQUESTED IT (agent, Connected by member, time, linked task), then exact read-only selectable payload with copy control and wrapped long strings, then Approve (single gold) and Reject (secondary outlined), then result showing who decided and when. Approved means authorised, not executed. Only confirmed execution can produce Succeeded. Payload unavailable means approval unavailable, with an explanation. No Approve all. No side-by-side approval grid.
- Task board: five columns only, To do, In progress, In review, Done, Failed, minimum 280px per column, 16px column gap, 12px card gap, 16px card padding, Georgia 18px column heading, small count, board-contained horizontal scroll on desktop/tablet, no whole-page overflow, no shrinking text. Mobile below about 768px: one list, status filter, status pill per task, no kanban. Dragging cannot be the only status control. No due date, priority, estimate, or progress percentage invented in the board view.
- Agents list: Agent, Connected by, Status, Current task, Last seen, about 64-72px rows, agent name more prominent than model/provider, no robot avatar, filter by the five supported agent states. Detail order: current task or idle explanation, pending approval, capabilities and permission scope, latest report, recent activity, technical logs last.
- Activity: sentence rows, about 56-72px, body 14px/22px, timestamp 13px, grouped Today, Yesterday, then date, actor plus action plus linked object plus context. Never raw event names, UUIDs, or JSON as the main message. Keep permission, execution, and verification as separate events.
- Settings: account settings separate from workspace settings, forms about 640px max, 24px section spacing, scoped Save, destructive actions below a divider, neutral explicit controls, no large red danger card, credentials masked, no nonfunctional settings for unimplemented features.

## Backend dependencies, flagged, not faked
- Member display name for Connected by: confirm the trusted source (workspace member profile, auth profile, or invite record) before rendering names. Do not invent a name or show an ID.
- Activity sentences: confirm the recorded event payload has actor, object, and outcome fields. If only `event_type` is stored, a sentence catalogue needs a data change or a documented fallback, not fabricated history.
- Approval consequence: destination, recipients, cost, and reversibility can only be shown where the payload actually carries them. Do not fabricate metadata for an approval.
- Approval safeguards: confirm server-side decide-once, version or changed-payload refresh, and already-decided handling before claiming the queue is safe. Frontend-only checks are not a safeguard.
- Execution versus approval: approving enqueues an execution in code comments, but the UI must not say Succeeded until execution is confirmed. If the worker path is not live, say so on the approvals page.
- Recovery: confirm a working Supabase password-recovery route and email template before adding a forgot-password link. A dead link is worse than a missing link.
- Invitation continuity: confirm `/join/[code]` preserves the invite through signup and sign-in and returns the member to the invited workspace. That flow was not inspected in this turn.
- Resend confirmation: only show resend if Supabase resend is actually wired. The current form does not show it.
- Priority and due date: tasks already store priority and due date, but the brief says not to invent them. Decide whether to keep them as existing product fields, hide them from the board, or remove them, as a product decision, not a silent UI edit.
